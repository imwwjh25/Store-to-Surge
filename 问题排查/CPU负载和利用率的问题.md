当 CPU 出现 “高负载但低利用率” 的情况时，核心原因是**CPU 处于 “等待” 状态而非 “执行” 状态**—— 即系统中存在大量需要 CPU 处理的任务，但这些任务因等待外部资源（如 I/O、锁、内存）而无法真正占用 CPU，导致 CPU 资源被 “闲置” 却无法释放给其他任务。以下从 “核心原因拆解”“排查步骤”“解决方案” 三方面详细说明：

### 一、先理解：CPU 负载 vs 利用率的本质区别

在排查前需明确两个指标的定义，避免混淆：



| 指标           | 核心含义                                                     | 单位           | 高值说明                          |
| -------------- | ------------------------------------------------------------ | -------------- | --------------------------------- |
| **CPU 负载**   | 等待 CPU 处理的**任务队列长度**（包括 “正在运行” 和 “等待运行” 的任务） | 数值（如 1.5） | 队列拥堵，任务排队等待 CPU        |
| **CPU 利用率** | CPU 实际用于 “执行计算任务” 的时间占比（分为用户态`us`、系统态`sy`等） | 百分比（%）    | CPU 在 “干活”，而非 “闲置 / 等待” |



**高负载低利用率的本质**：任务队列很长，但队列中的任务都在 “等别的东西”（如硬盘读数据、网络响应、锁释放），CPU 没事干，只能空等这些任务 “准备好”—— 相当于 “工厂里排队的工人很多，但工人都在等原材料，机器（CPU）空转”。

### 二、核心原因：哪类问题会导致 “CPU 等资源”？

按 “资源等待类型” 可分为 4 大类，覆盖 90% 以上场景：

#### 1. I/O 等待过高（最常见）

CPU 的计算速度远快于磁盘（HDD/SSD）、网络、外设（如打印机）的读写速度。当任务需要读取磁盘文件、发送网络请求时，CPU 会触发 I/O 操作，然后进入**等待 I/O 完成**的状态（对应系统指标`iowait`，简称`wa`）—— 此时任务占着 “负载队列”，但 CPU 实际没在干活，导致利用率低。



**典型场景**：



- 机械硬盘（HDD）大量随机读写（如数据库全表扫描、日志文件高频追加）；
- 网络带宽饱和（如服务器同时处理上千个慢网络请求，CPU 等数据传输完成）；
- 外接设备故障（如 U 盘卡住、打印机离线，CPU 等待设备响应）。

#### 2. 进程 / 线程 “阻塞”（锁竞争、资源抢占）

多任务环境中，进程 / 线程需通过 “锁”（如互斥锁、信号量）保护共享资源（如内存数据、文件句柄）。当多个任务竞争同一把锁时，未抢到锁的任务会进入**阻塞状态**—— 它们会被计入 “负载队列”，但无法使用 CPU，导致利用率低。



**典型场景**：



- 多线程程序中，大量线程竞争同一把互斥锁（如所有线程都要写同一个全局变量）；
- 数据库锁等待（如多个事务同时更新同一行数据，未获取行锁的事务阻塞）；
- 系统资源耗尽（如文件句柄用尽、端口被占，新任务无法创建句柄而阻塞）。

#### 3. 内存问题（Swap 频繁、内存泄漏）

内存是 CPU 与 I/O 之间的 “桥梁”：任务需先加载到内存中才能被 CPU 处理。若内存不足，系统会启用**Swap 分区**（将硬盘模拟为内存），但硬盘速度远慢于内存，导致任务频繁在 “内存 - Swap” 之间切换，CPU 大量时间用于 “等待内存数据就绪”。



**典型场景**：



- 内存泄漏（程序持续申请内存但不释放，如 Java 内存溢出、C++ 野指针），导致内存耗尽，Swap 使用率飙升；
- 大内存任务（如数据分析、虚拟机）运行时，内存不足触发频繁 Swap（即 “内存颠簸”）；
- 缓存失效（如数据库缓存未命中，每次查询都要读硬盘，CPU 等硬盘数据）。

#### 4. 系统配置 / 调度问题（CPU 亲和性、调度策略）

Linux/Unix 系统中，CPU 调度器负责分配 CPU 资源给任务，若调度配置不合理，会导致任务 “排队却拿不到 CPU”：



- **CPU 亲和性配置错误**：将任务绑定到某几个 CPU 核心，但这些核心已被其他任务占满，其他核心空闲却无法使用；
- **调度策略不当**：使用 “批处理调度策略”（如`SCHED_BATCH`）处理实时任务，导致任务调度延迟，队列堆积；
- **中断风暴**：硬件（如网卡、磁盘控制器）频繁触发 CPU 中断（如每秒数万次中断），CPU 虽在处理中断，但用户态任务无法被调度，表现为 “系统态利用率（sy）高，但用户态利用率（us）低”，整体利用率仍偏低。

### 三、分步排查：从 “系统指标” 到 “具体进程”

排查需遵循 “先看全局指标→再定位异常进程→最后分析进程行为” 的逻辑，推荐使用 Linux 系统工具（Windows 可类比）：

#### 第一步：查看全局 CPU 状态，确认 “等待类型”

使用`top`或`mpstat`工具，重点关注以下指标（以`top`为例，按`1`可显示所有 CPU 核心）：








```bash
top - 14:30:00 up 2 days,  1:20,  2 users,  load average: 8.50, 7.20, 6.80  # 负载（1/5/15分钟）
%Cpu(s):  5.2 us, 10.3 sy,  0.0 ni, 20.5 id, 63.8 wa,  0.0 hi,  0.2 si,  0.0 st
# 关键指标：
# us：用户态利用率（正常任务执行）；sy：系统态利用率（内核操作）
# id：空闲率（CPU没事干）；wa：I/O等待率（CPU等I/O，核心重点！）
# hi：硬中断率；si：软中断率（中断风暴看这两个）
```



- **若 wa（I/O 等待）>20%**：优先排查 I/O 问题；
- **若 sy（系统态）>30% 且 hi/si 高**：排查中断风暴或内核锁竞争；
- **若 id（空闲率）>50% 且负载高**：排查进程阻塞（锁等待、资源耗尽）；
- **若 Swap 使用率 > 50%**：排查内存问题（内存泄漏、Swap 颠簸）。

#### 第二步：定位异常进程（谁在占负载？）

使用`ps`或`htop`工具，查看 “阻塞状态的进程”，重点关注**进程状态（STAT）** 和**等待通道（WCHAN）**：








```bash
# 查看所有进程的状态、PID、负载贡献，按CPU负载排序
ps -eo pid,ppid,stat,%cpu,%mem,wchan,cmd --sort=-%cpu | head -20
```



- 进程状态（STAT）解读：

  - `D`：不可中断睡眠（等待 I/O，如磁盘读写，最常见高负载低利用率状态）；
  - `R`：运行中（正在用 CPU，若大量 R 进程则是真高利用率）；
  - `S`：可中断睡眠（等待锁、信号，如等待网络响应）；
  - `Z`：僵尸进程（已退出但未被父进程回收，虽不占 CPU 但占负载队列，需清理）。

- 等待通道（WCHAN）解读：显示进程在等什么资源，如：

  - `io_schedule`：等待 I/O 完成（磁盘 / 网络）；
  - `mutex_lock`：等待互斥锁；
  - `swapin`：等待 Swap 数据加载到内存；
  - `netpoll`：等待网络数据。



**示例**：若`ps`输出中大量进程 STAT 为`D`、WCHAN 为`io_schedule`，则可确定是 I/O 问题导致的高负载。

#### 第三步：针对 “等待类型” 深入排查

根据第一步和第二步的结论，定向排查具体问题：

##### 场景 1：I/O 等待高（wa>20%）

1. **用`iostat`看磁盘 I/O**：


   

   

   ```bash
   iostat -x 1  # 每秒输出一次磁盘I/O详情
   # 关键指标：
   # %util：磁盘利用率（接近100%表示磁盘满负荷）；
   # rMB/s/wMB：读写速度（是否达到磁盘上限，如HDD约100MB/s，SSD约500MB/s）；
   # avgqu-sz：磁盘请求队列长度（>5表示队列拥堵）
   ```

   - 若某磁盘（如`sda`）% util=100% 且 avgqu-sz>10：磁盘是瓶颈，需查看哪个进程在读写该磁盘。

2. **用`pidstat`定位 I/O 密集进程**：


   

   

   

   ```bash
   pidstat -d 1  # 每秒输出一次进程I/O统计
   # 关键指标：
   # kb_rd/s：进程每秒读磁盘量；kb_wr/s：每秒写磁盘量
   ```

   - 若某进程（如`mysql`）kb_rd/s 持续 > 50MB/s：该进程的磁盘读写是 I/O 瓶颈（如 MySQL 全表扫描）。

3. **用`iftop`看网络 I/O**：

   

   

   ```bash
   iftop  # 实时显示网络带宽使用
   ```

   - 若某网卡（如`eth0`）带宽接近上限（如 1G 网卡跑满 1000Mbps）：网络是瓶颈，需查看哪个进程在占用带宽（用`netstat -tulnp`看进程端口）。

##### 场景 2：进程阻塞（STAT=S/D，WCHAN = 锁 / 信号）

1. **用`pstack`查看进程调用栈**：


   

   

   

   ```bash
   pstack [PID]  # 打印进程的线程调用栈，看是否卡在锁等待
   ```

   - 示例：若输出中大量线程显示`pthread_mutex_lock`（互斥锁等待）：说明该进程存在锁竞争，需优化代码（如减少锁粒度、用无锁数据结构）。

2. **用`strace`跟踪进程系统调用**：


   

   

   

   ```bash
   strace -p [PID]  # 实时跟踪进程的系统调用，看是否卡在某步
   ```

   - 若输出持续显示`wait4()`（等待子进程）或`recvfrom()`（等待网络数据）：进程在等待外部资源，需排查子进程状态或网络链路。

3. **数据库锁等待排查**（以 MySQL 为例）：



   

   ```sql
   # 查看当前锁等待情况
   SELECT * FROM INFORMATION_SCHEMA.INNODB_LOCK_WAITS;
   # 查看正在运行的事务
   SHOW ENGINE INNODB STATUS;
   ```

   - 若输出中存在`LOCK_MODE='X'`（排他锁）的等待：说明事务间存在行锁竞争，需优化 SQL（如减少事务范围、加索引避免全表扫描）。

##### 场景 3：内存问题（Swap 高、内存泄漏）

1. **用`free`看内存 /swap 使用**：

   

   

   ```bash
   free -h  # 人性化显示内存状态
   # 关键指标：
   # available：可用内存（<10%表示内存不足）；
   # Swap：used列（>50%表示Swap频繁使用）
   ```

2. **用`vmstat`看内存交换频率**：


   

   

   

   

   ```bash
   vmstat 1  # 每秒输出一次内存/swap统计
   # 关键指标：
   # si：每秒从Swap读入内存的大小；so：每秒从内存写入Swap的大小
   # 若si/so持续>100KB：说明内存颠簸，需增加物理内存或优化进程内存占用
   ```

3. **用`jmap/jstat`排查 Java 内存泄漏**（若有 Java 进程）：



   

   

   

   ```bash
   # 查看Java进程内存分布
   jmap -heap [JavaPID]
   # 查看垃圾回收频率（若Full GC每秒多次，说明内存泄漏）
   jstat -gc [JavaPID] 1000
   ```

##### 场景 4：系统调度 / 中断问题

1. **用`cat /proc/interrupts`看中断分布**：

   

   

   

   ```bash
   cat /proc/interrupts | grep -E 'eth0|sda'  # 查看网卡/磁盘的中断次数
   ```

   - 若某 CPU 核心的中断次数每秒增长数万次（如网卡中断）：可能是中断风暴，需调整中断均衡（用`irqbalance`工具）。

2. **用`taskset`查看 CPU 亲和性**：

   

   

   ```bash
   # 查看进程绑定的CPU核心（如PID 1234绑定在核心0-3）
   taskset -cp 1234
   # 若绑定的核心已占满，可重新绑定到空闲核心
   taskset -cp 4-7 1234
   ```

### 四、常见解决方案汇总

| 问题类型        | 解决方案                                                     |
| --------------- | ------------------------------------------------------------ |
| I/O 瓶颈        | 1. 替换机械硬盘为 SSD/NVMe；2. 优化 I/O 操作（如批量读写、使用缓存）；3. 升级网络带宽 |
| 锁竞争          | 1. 减少锁粒度（如用分段锁替代全局锁）；2. 使用无锁数据结构（如 Java 的 ConcurrentHashMap）；3. 优化数据库事务（短事务、索引优化） |
| 内存不足 / 泄漏 | 1. 增加物理内存；2. 排查并修复内存泄漏（如 Java 用 MAT 分析 dump 文件）；3. 禁用 Swap（仅适合内存充足场景） |
| 中断风暴        | 1. 启用`irqbalance`服务均衡中断；2. 配置网卡多队列（RSS）分散中断压力；3. 升级硬件驱动 |
| CPU 亲和性错误  | 1. 用`taskset`重新绑定进程到空闲 CPU 核心；2. 避免过度绑定，让调度器自动分配 |

### 总结

“高负载低利用率” 的核心是 **“任务等资源，CPU 空转”**，排查时需先通过`top`确认 “等待类型”（I/O、锁、内存、调度），再用针对性工具（`iostat`/`pstack`/`vmstat`）定位具体进程和资源瓶颈，最后根据问题类型优化硬件、代码或配置 —— 本质是减少 “任务等待时间”，让 CPU 能真正 “干活”。
