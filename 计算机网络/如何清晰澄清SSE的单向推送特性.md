# 一、直接给结论（最关键）

**SSE = Server-Sent Events，全称：服务器发送事件**

从名字就能看出来：

- 只有 **服务器 → 客户端** 一个方向
- **客户端 → 服务器** 无法通过同一个 SSE 连接发送任何数据
- **SSE 是标准的半双工 / 单向推送协议**

一句话：

**SSE 只能 “推”，不能 “收”；只能 “说话”，不能 “听话”。**

------

# 二、为什么 SSE 绝对不能双工？（底层原理）

SSE 基于 **HTTP 协议**运行，且严格遵循 HTTP 的请求 / 响应模型：

1. **客户端发送一个 GET 请求**
2. **服务器保持连接打开，持续向下推送数据流**
3. **这个连接从请求发出去后，就只能读，不能再写**

HTTP 请求是**单向通道**：

- 请求头发送完毕 → 通道变成**只读**
- 客户端**无法再向这个连接写入任何数据**

这就是 SSE 无法双工的**本质原因**。

------

# 三、最清晰的对比：SSE 单向 vs WebSocket 全双工

表格







|         特性         |                SSE                 |             WebSocket              |
| :------------------: | :--------------------------------: | :--------------------------------: |
|       通信方向       |      **只能服务器 → 客户端**       |    **服务器 ↔ 客户端 双向自由**    |
|       连接类型       |            HTTP 单向流             |          独立全双工套接字          |
| 客户端能否主动发消息 |   **不能（必须新开 HTTP 请求）**   |      **能（同一连接随时发）**      |
|       真正双工       |            ❌ 绝对不支持            |             ✅ 原生支持             |
|       适合场景       | 实时通知、大模型流式输出、日志推送 | 聊天、游戏、实时交互、频繁双向通信 |

# 四、如何**清晰、无歧义**地解释 SSE 的单向性？

你可以用下面这 3 句最精准的话向任何人解释：

### 1. 协议定义级解释

**SSE 是 HTTP 协议上的单向流式推送，客户端只能接收，不能通过该连接发送数据。**

### 2. 通俗解释

**SSE 像收音机：你只能听，不能说话；服务器一直播，你只能收。**

### 3. 技术严谨解释

**SSE 建立的是只读响应流，请求发送后通道方向固定，不支持上行数据，因此不具备双工能力。**

# 五、最容易误解的误区澄清（非常重要）

## ❌ 误区 1：我可以用 AJAX 配合 SSE 实现双向，所以 SSE 是双工

**错！**

- SSE 负责：服务器 → 客户端
- AJAX 负责：客户端 → 服务器

这是**两个独立连接**，不是 SSE 本身具备双工能力。

就像：

你用**收音机听广播** + **发短信** ≠ 收音机具备通话功能。

## ❌ 误区 2：HTTP/2 支持多路复用，所以 SSE 能双工

**错！**

HTTP/2 只是能并行多个流，但每个流依然是：

**一个请求 + 一个响应（单向）**

方向依然固定，SSE 依然只能下行。

## ❌ 误区 3：SSE 长连接 = 双向通道

**错！**

SSE 的 “长连接” 只是**响应不断开**，不是双向通道。

方向永远是：

**客户端请求 → 服务器持续响应**

中途不能反向传输。

------

# 六、最终权威结论（可直接用于面试 / 文档）

1. **SSE 不具备任何形式的双工通信能力**
2. SSE 是**严格单向推送**：服务器 → 客户端
3. 客户端无法在 SSE 连接上发送数据，必须新建 HTTP 请求
4. SSE 和 WebSocket 的最本质区别就是：**单向 vs 全双工**
