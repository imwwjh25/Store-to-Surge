## 什么是「打破双亲委派」？

不按 “先找父加载器” 的顺序，**自己先加载类**，绕开顶层类加载器。

------

# 一、Java 中**典型打破双亲委派**的 4 大场景（背这 4 个就够）

## 1. **SPI 机制（最常考！Service Provider Interface）**

### 场景

JDBC、JNDI、JDBC、Spring、Dubbo 都用。

### 为什么打破？

- JDBC 接口（`java.sql.Driver`）是 **Bootstrap 类加载器**加载的
- 但 JDBC 实现类（MySQL 驱动 `com.mysql.cj.jdbc.Driver`）在项目 jar 里，是 **App 类加载器**加载
- Bootstrap 加载器**找不到**项目里的驱动类
- 所以必须**用线程上下文类加载器（Thread.getContextClassLoader ()）** 去加载，绕开双亲委派

### 面试回答：

SPI 接口由 Bootstrap 加载，但实现类在应用 ClassPath 下，父加载器找不到，

所以用**线程上下文类加载器**（默认是 AppClassLoader）加载实现类，**打破双亲委派**。

------

## 2. **热部署 / 热加载（JRebel、Spring Boot DevTools）**

### 场景

代码修改后不用重启，自动更新类。

### 为什么打破？

- 每个热部署模块用**自己独立的 ClassLoader**
- 不委托给父类加载，自己直接加载新类
- 实现类的重新加载

### 面试回答：

热部署需要反复加载新版本类，必须自定义 ClassLoader，**不遵守双亲委派**，自己加载最新的类文件。

------

## 3. **OSGi 模块化框架**

### 场景

Eclipse、插件化开发。

### 为什么打破？

- 每个模块（Bundle）有自己的类加载器
- 模块之间互相依赖，**不向上委托**，而是互相加载
- 完全破坏双亲委派模型

### 面试回答：

OSGi 为了实现模块化、插件化，每个模块有独立类加载器，**不委托父加载器**，而是模块间互相加载，打破双亲委派。

------

## 4. **Tomcat 服务器（必考！）**

### 场景

一个 Tomcat 运行多个 Web 应用。

### 为什么打破？

- 不同 war 包**可能有相同类名、不同版本**
- 如果按双亲委派，所有应用共用一个类，会冲突
- 所以每个 WebApp 用**自己的 WebAppClassLoader**
- **先自己加载，加载不到才交给父类**

### 面试回答：

Tomcat 为了让**不同应用的类相互隔离**，每个 Web 应用使用独立的类加载器，优先自己加载，打破双亲委派。

------

# 二、面试官最爱问：怎么打破？（底层方法）

你直接背这 2 个方法：

1. **重写 `ClassLoader.loadClass()` 方法**

   

   - 默认是双亲委派逻辑
   - 重写后不交给父类，就打破了

   

2. **使用 `Thread.getContextClassLoader()` 线程上下文类加载器**

   

   - 让顶层类加载器（Bootstrap）能拿到底层 AppClassLoader
   - SPI 就是这么干的

   

------

# 三、面试满分回答模板（直接背）

Java 中打破双亲委派机制的常见场景有：

1. **SPI 机制**：如 JDBC，接口由 Bootstrap 加载，但实现类在应用路径下，通过**线程上下文类加载器**加载实现，打破双亲委派。
2. **Tomcat 容器**：为了**类隔离**，每个 Web 应用用独立类加载器，优先自己加载。
3. **热部署**：如 JRebel，自定义类加载器实现类的重复加载。
4. **OSGi 模块化**：每个插件独立加载，互相委托，不遵循双亲委派。

打破的核心方式：**重写 loadClass () 方法** 或 **使用线程上下文类加载器**。

------

### 总结

1. 打破双亲委派 **4 大场景**：**SPI、Tomcat、热部署、OSGi**
2. 最常考：**SPI（JDBC）** 和 **Tomcat**
3. 打破方法：**重写 loadClass**、**线程上下文类加载器**
