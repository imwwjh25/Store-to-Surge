### 一、先拆解哈希表的取值逻辑

哈希表取值的核心步骤：

1. 对目标键 `key` 计算哈希值：`hash = hash_func(key)`（这一步是纯计算，严格 O (1)）；
2. 根据哈希值找到对应的 “桶（Bucket）”：`bucket = table[hash % capacity]`（数组下标访问，严格 O (1)）；
3. 若桶内无冲突（只有一个元素），直接返回值；若有冲突（多个元素在同一个桶），则遍历桶内元素（比如链表 / 红黑树）找到匹配的 `key`。

**关键矛盾**：第三步的 “冲突处理” 是时间复杂度的变量 —— 冲突越少，耗时越接近 O (1)；冲突越多，耗时越高（最坏 O (n)）。

### 二、“平均 O (1)” 的数学依据

“平均” 的本质是**在 “哈希函数均匀分布” 的理想假设下，冲突的期望次数趋近于常数**，具体分两层理解：

#### 1. 前提假设：哈希函数是 “均匀的”

一个好的哈希函数会满足：

- 不同的 `key` 被映射到不同哈希值的概率尽可能高；
- 所有 `key` 的哈希值均匀分布在哈希表的所有桶中，即每个桶被命中的概率相等。

比如哈希表有 `m` 个桶，存入 `n` 个元素，**负载因子**`α = n/m`（表示每个桶平均存放的元素数）。

在均匀哈希假设下，每个桶中的元素数量期望为 `α`（负载因子）。

#### 2. 平均时间复杂度的推导

- 哈希表的**负载因子**通常被设计为常数（比如 Java 的 HashMap 默认负载因子是 0.75），即 `α = n/m ≈ C`（C 是固定常数，比如 0.75）；
- 取值时，找到桶的时间是 O (1)，遍历桶内元素的期望次数是 `α`（常数）；
- 因此，**单次取值的平均时间复杂度 = O (1) + O (α) = O (1)**（常数级时间属于 O (1)）。

### 三、用例子直观理解 “平均”

假设：

- 哈希表容量 `m=100`（100 个桶），负载因子 `α=0.75`，即最多存 `75` 个元素；
- 哈希函数均匀分布，75 个元素会分散在 100 个桶中，大部分桶只有 1 个元素，少数桶有 2 个元素（几乎不会出现更多）。

统计 1000 次取值操作：

- 900 次：桶内无冲突，耗时 O (1)；
- 100 次：桶内有 1 次冲突，遍历 2 个元素，耗时 O (1)（常数级）；
- 总平均耗时 = (900×1 + 100×2) / 1000 = 1.1 次操作 → 仍属于 O (1)。

### 四、补充：最坏情况 vs 平均情况



|   场景   | 时间复杂度 |                           触发条件                           |
| :------: | :--------: | :----------------------------------------------------------: |
| 平均情况 |    O(1)    |                  哈希函数均匀，负载因子可控                  |
| 最坏情况 |    O(n)    | 所有 key 哈希值相同（比如哈希函数设计缺陷），所有元素挤在一个桶里 |

实际工程中，哈希表会通过以下方式避免最坏情况：

1. 动态扩容：当负载因子超过阈值（如 0.75），自动扩容为原来的 2 倍，降低冲突概率；
2. 冲突优化：Java 8 后，HashMap 的桶内元素超过 8 个时，链表转为红黑树，最坏时间复杂度从 O (n) 优化为 O (log n)。

### 总结

1. 哈希表取值的 “平均 O (1)” 是基于**哈希函数均匀分布**和**负载因子为常数**的统计结论；
2. “平均” 指大量操作的**期望耗时**为常数级，而非单次操作绝对 O (1)；
3. 工程上通过控制负载因子、优化冲突处理（链表→红黑树），让实际性能无限接近平均 O (1)。

简单来说：只要哈希函数设计合理、哈希表不超载，绝大多数情况下取值都是一次定位，少数冲突的情况也只是常数次遍历，整体平均下来就是 O (1)。
