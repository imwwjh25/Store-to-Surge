分布式事务是解决**跨多个数据库 / 服务**的数据一致性问题的核心方案，其核心目标是保证分布式场景下「要么所有操作成功，要么所有操作回滚」，符合 ACID 特性（分布式场景下侧重最终一致性 / 强一致性）。下面从核心概念、2PC/3PC（理论协议）、Seata/TCC（落地实现）逐一拆解，结合场景和优缺点讲清楚：

### 一、先明确：分布式事务的核心问题

单机事务靠数据库锁 / 日志就能保证 ACID，但分布式场景下：

- 网络不可靠（超时、断连）；

- 节点故障（数据库 / 服务挂了）；

- 各节点操作无法原子化（比如 A 服务扣库存、B 服务创订单，一个成一个败）；

  

  因此需要一套协议 / 框架来协调多个节点的事务行为。

------

### 二、2PC（Two-Phase Commit，两阶段提交）

#### 1. 核心定义

2PC 是**强一致性**的分布式事务协议，将事务分为「准备阶段」和「提交阶段」，由「协调者（Coordinator）」统一指挥「参与者（Participant）」，是分布式事务最基础的理论模型（数据库的 XA 事务就是 2PC 的实现）。

#### 2. 执行流程

| 阶段               | 协调者行为                                                   | 参与者行为                                                   |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 准备阶段（Vote）   | 1. 向所有参与者发送「准备提交」请求；2. 等待所有参与者的反馈。 | 1. 执行本地事务（写数据、加锁），但**不提交**；2. 记录事务日志（保证崩溃后可恢复）；3. 反馈「同意提交」（可执行）或「拒绝提交」（执行失败）。 |
| 提交阶段（Commit） | 情况 1：所有参与者反馈「同意」→ 发送「全局提交」指令；情况 2：任意参与者反馈「拒绝」→ 发送「全局回滚」指令。 | 情况 1：执行本地提交，释放锁；情况 2：执行本地回滚，释放锁；反馈最终结果给协调者。 |

#### 3. 核心特点

- **强一致性**：只要流程正常，能保证所有节点要么都提交，要么都回滚；
- **阻塞性**：准备阶段后，参与者会持有锁（直到提交 / 回滚），若协调者故障，参与者会一直阻塞，导致资源锁定；
- **单点故障**：协调者是核心，若协调者在提交阶段崩溃，部分参与者可能提交、部分未提交，出现「数据不一致」；
- **简单易实现**：数据库 XA 事务（如 MySQL 的 XA）、早期分布式框架（如 DTP）都是基于 2PC。

#### 4. 优缺点

| 优点               | 缺点                                                         |
| ------------------ | ------------------------------------------------------------ |
| 强一致性，逻辑简单 | 1. 阻塞问题：准备阶段后锁资源不释放，性能差；2. 协调者单点故障风险；3. 脑裂问题：协调者崩溃后，部分节点提交、部分未提交；4. 无法处理网络超时（比如参与者反馈丢失）。 |

#### 5. 适用场景

仅适合「短事务、低并发、强一致性要求高」的场景（如金融核心交易），互联网场景极少直接用纯 2PC（性能瓶颈太明显）。

------

### 三、3PC（Three-Phase Commit，三阶段提交）

#### 1. 核心定义

3PC 是对 2PC 的改进，解决 2PC 的「阻塞问题」和「单点故障导致的不一致」，分为「准备阶段（CanCommit）」、「预提交阶段（PreCommit）」、「提交阶段（DoCommit）」，新增「超时机制」。

#### 2. 执行流程

| 阶段                    | 协调者行为                                                   | 参与者行为                                                   |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 准备阶段（CanCommit）   | 1. 向参与者发送「是否可执行」请求；2. 等待反馈。             | 1. 仅做「可行性检查」（不执行事务、不加锁）；2. 反馈「可执行」或「不可执行」。 |
| 预提交阶段（PreCommit） | 情况 1：所有参与者反馈「可执行」→ 发送「预提交」指令；情况 2：任意参与者反馈「不可执行」→ 发送「中断」指令。 | 情况 1：执行本地事务（写数据、加锁），但不提交；情况 2：直接中断，无操作。 |
| 提交阶段（DoCommit）    | 情况 1：收到所有参与者预提交成功反馈 → 发送「全局提交」；情况 2：超时 / 收到失败反馈 → 发送「全局回滚」；（核心：协调者超时默认回滚） | 情况 1：提交事务，释放锁；情况 2：回滚事务，释放锁；（核心：参与者超时默认提交）。 |

#### 3. 核心改进

- 拆分 2PC 的准备阶段为「CanCommit（无锁）+ PreCommit（有锁）」，减少锁持有时间；
- 引入超时机制：协调者超时→回滚，参与者超时→提交（降低阻塞概率）；
- 降低单点故障影响：即使协调者崩溃，参与者超时后会自动提交，避免永久阻塞。

#### 4. 优缺点

| 优点                       | 缺点                                                         |
| -------------------------- | ------------------------------------------------------------ |
| 减少阻塞，降低单点故障影响 | 1. 仍有数据不一致风险：参与者超时自动提交，但若协调者实际发的是回滚指令，会导致部分节点提交；2. 流程更复杂，实现成本高；3. 仍无法完全解决网络分区问题。 |

#### 5. 适用场景

极少落地使用（理论改进但实际问题仍存在），仅作为分布式事务协议的理论补充，工业界几乎没有主流框架基于 3PC 实现。

------

### 四、Seata（阿里开源分布式事务框架）

#### 1. 核心定义

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里开源的轻量级分布式事务框架，支持多种事务模式（AT/TCC/SAGA/XA），解决了传统 2PC 的性能问题，适配微服务场景（Spring Cloud/Dubbo）。

#### 2. Seata 的核心角色

- **TC（Transaction Coordinator）**：事务协调者，全局事务的管理者，负责创建 / 提交 / 回滚全局事务；
- **TM（Transaction Manager）**：事务管理器，发起全局事务，向 TC 注册全局事务，触发提交 / 回滚；
- **RM（Resource Manager）**：资源管理器，管理分支事务（本地事务），向 TC 注册分支事务，执行本地提交 / 回滚。

#### 3. Seata 的核心模式（重点讲 AT 和 TCC）

##### （1）AT 模式（Seata 默认，最常用）

- **核心思想**：基于 2PC 的改进，「无侵入」（业务代码无需修改），通过「自动生成回滚日志」实现最终一致性；

- 执行流程：

  1. 准备阶段：RM 执行本地 SQL，记录「前后镜像」（回滚日志），加行锁，向 TC 注册分支事务；
  2. 提交阶段：TC 通知 RM 提交，RM 删除回滚日志，释放锁（异步提交，性能高）；
  3. 回滚阶段：TC 通知 RM 回滚，RM 根据回滚日志恢复数据，释放锁。

- 优缺点：

  

  ✅ 优点：无侵入、适配关系型数据库、性能接近单机事务；

  

  ❌ 缺点：依赖数据库行锁、不支持非关系型数据库（如 MongoDB）、需要 Seata 服务端依赖。

##### （2）TCC 模式（Seata 支持，手动实现）

- **核心思想**：「侵入式」，将事务拆分为「Try-Confirm-Cancel」三个手动实现的阶段，不依赖数据库锁，适配非关系型数据库 / 异构系统；
- （下文会单独拆解 TCC，这里先关联 Seata 的支持：Seata 仅做 TCC 的事务协调，Try/Confirm/Cancel 的业务逻辑需开发者自己写）。

##### （3）SAGA 模式

- 适用于「长事务、异步场景」（如订单履约、物流流程），基于状态机实现，支持补偿逻辑，最终一致性；
- 优点：无锁、支持长事务；缺点：一致性弱，需手动写补偿逻辑。

##### （4）XA 模式

- 基于数据库 XA 协议的 2PC 实现，强一致性；
- 优点：强一致；缺点：阻塞、性能差，仅适合金融场景。

#### 4. Seata 的核心优势

- 适配微服务生态（Spring Cloud/Dubbo/MyBatis）；
- 多种事务模式适配不同场景；
- 性能优于传统 2PC（AT 模式异步提交）；
- 易部署（支持单机 / 集群）。

------

### 五、TCC（Try-Confirm-Cancel，补偿事务）

#### 1. 核心定义

TCC 是「侵入式、业务层」的分布式事务方案，不依赖数据库锁，通过手动拆分业务逻辑为三个阶段，实现最终一致性，是互联网场景最常用的分布式事务方案之一（Seata 可协调 TCC，但 TCC 本身是一种设计模式）。

#### 2. 核心阶段（必须手动实现）

| 阶段    | 核心目标                                                     | 业务示例（订单 + 库存场景）                                  |
| ------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Try     | 1. 检查资源（库存是否足够）；2. 预留资源（冻结库存，不扣减）；3. 保证幂等（防重复调用）。 | 冻结商品库存（如库存 100→冻结 10，可用 90），创建待支付订单。 |
| Confirm | 1. 确认执行事务；2. 释放预留资源；3. 幂等 + 防悬挂（Try 未执行的话，Confirm 不执行）。 | 扣减冻结的库存（90→80），将订单状态改为「已支付」。          |
| Cancel  | 1. 取消事务；2. 释放预留资源；3. 幂等 + 防空回滚（Confirm 未执行的话，Cancel 才执行）。 | 解冻冻结的库存（90→100），将订单状态改为「已取消」。         |

#### 3. 执行流程

1. TM 向 TC 发起全局事务；
2. TC 协调所有 RM 执行 Try 阶段：
   - 所有 RM Try 成功 → 执行 Confirm 阶段；
   - 任意 RM Try 失败 → 执行 Cancel 阶段；
3. Confirm/Cancel 阶段由 TC 异步重试（保证最终执行成功）。

#### 4. 核心设计要点（必须解决）

- **幂等性**：Try/Confirm/Cancel 可能被重复调用（网络重试），需保证多次调用结果一致（如通过订单 ID + 阶段标记做幂等）；
- **防悬挂**：Cancel 先执行（Try 超时未执行），导致预留资源不存在，需拒绝 Cancel；
- **防空回滚**：Confirm 执行前，Try 未成功，需拒绝 Confirm；
- **补偿重试**：Confirm/Cancel 失败时，需异步重试（如定时任务），直到成功。

#### 5. 优缺点

| 优点                                                         | 缺点                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| 1. 无锁，性能极高（互联网高并发场景首选）；2. 适配异构系统（数据库 / 缓存 / 消息队列）；3. 最终一致性，无阻塞； | 1. 侵入式开发，需手动写 Try/Confirm/Cancel 逻辑；2. 开发成本高（需处理幂等 / 重试 / 补偿）；3. 业务耦合度高。 |

#### 6. 适用场景

互联网高并发场景（如电商下单、支付、库存扣减）、异构系统交互（如跨数据库 / 跨服务 / 跨语言）。

------

### 六、核心对比（2PC/3PC/Seata/TCC）

| 维度     | 2PC            | 3PC                | Seata（AT）           | Seata（TCC）       |
| -------- | -------------- | ------------------ | --------------------- | ------------------ |
| 一致性   | 强一致         | 强一致（理论）     | 最终一致（接近强）    | 最终一致           |
| 阻塞性   | 严重阻塞       | 弱阻塞             | 弱阻塞（短锁）        | 无阻塞             |
| 侵入性   | 无（数据库层） | 无（数据库层）     | 无（业务层）          | 强（需手动写逻辑） |
| 性能     | 差             | 中                 | 优                    | 最优               |
| 适用场景 | 金融核心交易   | 几乎不用           | 微服务常规场景        | 高并发电商 / 支付  |
| 故障恢复 | 差（易不一致） | 中（超时自动处理） | 优（自动回滚 / 重试） | 中（需手动补偿）   |

------

### 七、落地建议

1. **优先选 Seata AT 模式**：无侵入、性能高，适配 80% 的微服务场景（如订单、库存、支付）；
2. **高并发 / 异构系统选 Seata TCC**：比如跨数据库 + 缓存 + 消息队列的场景，手动实现 Try/Confirm/Cancel；
3. **金融强一致选 2PC（XA）**：比如银行转账、证券交易；
4. **长事务选 Seata SAGA**：比如物流履约、工单流程；
5. **3PC 仅做理论了解**：工业界几乎无落地场景。

总结：分布式事务的核心是「在一致性和性能之间做权衡」，互联网场景优先「最终一致性」，金融场景优先「强一致性」，Seata 是目前最成熟的落地框架。
