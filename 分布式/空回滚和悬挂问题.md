### 先铺垫：TCC 的核心流程（快速回顾）

TCC 分为 3 个阶段：

- **Try**：资源检查和预留（比如检查库存是否足够，冻结对应数量的库存）
- **Confirm**：确认执行（真正扣减冻结的库存）
- **Cancel**：取消执行（解冻预留的库存）

「悬挂」和「空回滚」都是 TCC 在**网络异常、超时、重试**场景下的典型问题，且两者经常伴随出现。

------

## 一、空回滚（最常见）

### 1. 定义

**Cancel 阶段被提前执行，且 Try 阶段实际并未成功预留资源**，导致 Cancel 操作在「没有任何资源可回滚」的情况下执行，这就是空回滚。

### 2. 产生原因（电商场景举例）

比如用户下单扣库存的 TCC 流程：

1. 协调者调用库存服务的`try`方法（预留库存），但网络超时，协调者认为`try`失败；
2. 协调者触发全局回滚，调用库存服务的`cancel`方法；
3. 但实际上，`try`方法只是**网络延迟**，并非真的执行失败，只是结果没返回给协调者；
4. 此时`cancel`方法执行时，发现没有任何预留的库存（因为`try`还没执行完 / 没执行成功），这就是空回滚。

### 3. 为什么空回滚是问题？

如果`cancel`方法没有做空回滚防护，可能会：

- 抛出异常，导致全局事务回滚失败；
- 执行无意义的数据库操作，增加性能损耗；
- 若后续`try`方法又执行成功（比如超时后重试），会导致「预留了资源但没人取消 / 确认」，资源永久冻结。

### 4. 解决方案（电商场景代码示例）

核心：**在 Cancel 阶段先检查 Try 阶段是否真正执行成功，若未成功则直接返回成功（不抛异常）**。

java



运行









```
@Service
public class StockTccService {
    @Autowired
    private StockFreezeMapper freezeMapper; // 库存冻结表（记录Try阶段的预留资源）

    // ===== Try阶段：预留库存 =====
    @Transactional(rollbackFor = Exception.class)
    public boolean tryDeduct(Long skuId, Integer num, String xid) {
        // 1. 检查库存
        Stock stock = stockMapper.selectById(skuId);
        if (stock.getNum() < num) {
            return false;
        }
        // 2. 冻结库存（记录Try的结果，关键：用xid唯一标识全局事务）
        StockFreeze freeze = new StockFreeze();
        freeze.setSkuId(skuId);
        freeze.setNum(num);
        freeze.setXid(xid); // 全局事务ID，核心标识
        freeze.setStatus(1); // 1-已冻结
        freezeMapper.insert(freeze);
        // 3. 扣减可用库存
        stockMapper.deductAvailableStock(skuId, num);
        return true;
    }

    // ===== Cancel阶段：解冻库存（防空回滚核心） =====
    @Transactional(rollbackFor = Exception.class)
    public boolean cancelDeduct(String xid) {
        // 核心：先查Try阶段是否有预留记录
        StockFreeze freeze = freezeMapper.selectByXid(xid);
        if (freeze == null) {
            // 没有Try的预留记录，说明是空回滚，直接返回成功
            return true;
        }
        // 有预留记录，才执行解冻
        stockMapper.unfreezeStock(freeze.getSkuId(), freeze.getNum());
        freezeMapper.updateStatus(freeze.getId(), 0); // 0-已解冻
        return true;
    }
}
```

## 二、悬挂

### 1. 定义

**Cancel 阶段执行完成后，Try 阶段的请求才到达并执行成功**，导致「资源被预留，但没有后续的 Confirm/Cancel 来处理」，预留的资源被「悬挂」起来，永久无法释放。

### 2. 产生原因（电商场景举例）

比空回滚更极端的时序问题：

1. 协调者调用`try`方法，网络超时，判定`try`失败；
2. 协调者调用`cancel`方法，执行空回滚（返回成功）；
3. 但此时`try`方法的请求才到达库存服务，且执行成功（预留了库存）；
4. 由于全局事务已经回滚，协调者不会再调用`confirm`或`cancel`，导致预留的库存永久冻结，这就是悬挂。

### 3. 为什么悬挂是问题？

- 预留的资源（比如冻结的库存）无法释放，导致库存数据不一致；
- 用户下单失败，但库存被冻结，后续无法再次下单。

### 4. 解决方案（电商场景代码示例）

核心：**在 Try 阶段先检查全局事务是否已经执行过 Cancel，若已执行则直接返回失败，拒绝预留资源**。

java



运行









```
@Service
public class StockTccService {
    @Autowired
    private StockFreezeMapper freezeMapper;
    @Autowired
    private TccTransactionMapper tccTxMapper; // 记录全局事务状态的表

    // ===== Try阶段：防悬挂核心 =====
    @Transactional(rollbackFor = Exception.class)
    public boolean tryDeduct(Long skuId, Integer num, String xid) {
        // 核心步骤1：检查全局事务是否已取消
        TccTransaction tx = tccTxMapper.selectByXid(xid);
        if (tx != null && tx.getStatus() == 2) { // 2-已取消
            // 全局事务已回滚，拒绝执行Try，避免悬挂
            return false;
        }

        // 核心步骤2：检查是否已有该xid的冻结记录（防Try重试）
        StockFreeze existFreeze = freezeMapper.selectByXid(xid);
        if (existFreeze != null) {
            return existFreeze.getStatus() == 1; // 已有冻结则返回结果
        }

        // 原有Try逻辑：检查库存、冻结资源
        Stock stock = stockMapper.selectById(skuId);
        if (stock.getNum() < num) {
            return false;
        }
        StockFreeze freeze = new StockFreeze();
        freeze.setSkuId(skuId);
        freeze.setNum(num);
        freeze.setXid(xid);
        freeze.setStatus(1);
        freezeMapper.insert(freeze);
        stockMapper.deductAvailableStock(skuId, num);
        
        // 记录全局事务Try成功
        tccTxMapper.insertOrUpdate(xid, 1); // 1-Try成功
        return true;
    }

    // ===== Cancel阶段：增强（记录全局事务状态） =====
    @Transactional(rollbackFor = Exception.class)
    public boolean cancelDeduct(String xid) {
        // 1. 先记录全局事务状态为「已取消」
        tccTxMapper.insertOrUpdate(xid, 2);
        
        // 2. 原有空回滚防护逻辑
        StockFreeze freeze = freezeMapper.selectByXid(xid);
        if (freeze == null) {
            return true;
        }
        // 解冻库存
        stockMapper.unfreezeStock(freeze.getSkuId(), freeze.getNum());
        freezeMapper.updateStatus(freeze.getId(), 0);
        return true;
    }
}
```

## 三、悬挂 vs 空回滚（核心区别）

表格







|   维度   |              空回滚              |                 悬挂                 |
| :------: | :------------------------------: | :----------------------------------: |
| 核心时序 |    Cancel 先执行，Try 未成功     |      Cancel 执行完，Try 才成功       |
|   本质   |            回滚无资源            |          预留资源无后续处理          |
|   风险   |      事务回滚失败、性能损耗      |       资源永久冻结、数据不一致       |
| 防护核心 | Cancel 查 Try 记录，无则返回成功 | Try 查 Cancel 状态，已取消则返回失败 |

------

## 四、通用防护方案（落地必做）

无论是空回滚还是悬挂，核心解决思路都是**基于全局事务 ID（XID）记录各阶段的执行状态**，总结 3 个关键动作：

1. **记录状态**：在 Try 阶段记录「资源预留成功」的状态（关联 XID）；
2. **空回滚防护**：Cancel 阶段先查 XID 对应的 Try 状态，无则直接返回成功；
3. **悬挂防护**：Try 阶段先查 XID 对应的全局事务状态，若已取消则拒绝执行。

------

### 总结

1. **空回滚**：Cancel 阶段在 Try 未成功时执行，核心防护是「Cancel 先查 Try 记录，无则返回成功」；
2. **悬挂**：Cancel 执行后 Try 才成功，核心防护是「Try 先查全局事务状态，已取消则拒绝执行」；
3. 两者的根源都是分布式事务的**网络超时 / 重试**，解决关键是通过「XID + 状态表」追踪各阶段执行结果，避免无意义的操作和资源泄漏。
