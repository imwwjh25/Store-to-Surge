### 核心场景定义

**业务背景**：用户下单后，需要完成两个操作：

1. 本地事务：创建订单（订单库）

2. 远程事务：扣减商品库存（库存库）

   

   要求：两个操作要么都成功，要么都失败，不能出现「订单创建成功但库存没扣减」或「库存扣减但订单没创建」的情况。

------

## 一、本地消息表（最经典的最终一致性方案）

### 核心思想

把「远程调用」转化为「本地写消息表」，通过**本地事务保证消息写入和业务操作原子性**，再通过**定时任务重试发送消息**，确保远程操作最终执行成功。

### 实现步骤（电商下单场景）

#### 1. 数据库设计（核心是本地消息表）

sql











```
-- 订单表（业务表）
CREATE TABLE `tb_order` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '订单ID',
  `user_id` bigint NOT NULL COMMENT '用户ID',
  `sku_id` bigint NOT NULL COMMENT '商品SKU',
  `num` int NOT NULL COMMENT '购买数量',
  `status` tinyint NOT NULL DEFAULT 0 COMMENT '0-待付款 1-已付款',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

-- 本地消息表（核心）
CREATE TABLE `tb_local_message` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '消息ID',
  `biz_id` bigint NOT NULL COMMENT '关联业务ID（订单ID）',
  `biz_type` varchar(32) NOT NULL COMMENT '业务类型（order_create）',
  `message_content` json NOT NULL COMMENT '消息内容（库存扣减参数）',
  `status` tinyint NOT NULL DEFAULT 0 COMMENT '0-待发送 1-发送中 2-已成功 3-失败',
  `send_times` int NOT NULL DEFAULT 0 COMMENT '重试次数',
  `max_retry` int NOT NULL DEFAULT 3 COMMENT '最大重试次数',
  `next_retry_time` datetime NOT NULL COMMENT '下次重试时间',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_status_retry` (`status`,`next_retry_time`) COMMENT '定时任务查询索引'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

#### 2. 代码实现（核心：本地事务 + 定时任务）

##### 步骤 1：下单并写入本地消息表（本地事务保证原子性）

java



运行









```
@Service
public class OrderService {
    @Autowired
    private OrderMapper orderMapper;
    @Autowired
    private LocalMessageMapper localMessageMapper;
    @Autowired
    private RestTemplate restTemplate; // 调用库存服务

    // 本地事务：创建订单 + 写入消息表
    @Transactional(rollbackFor = Exception.class)
    public Long createOrder(Long userId, Long skuId, Integer num) {
        // 1. 创建订单（业务操作）
        Order order = new Order();
        order.setUserId(userId);
        order.setSkuId(skuId);
        order.setNum(num);
        orderMapper.insert(order);
        Long orderId = order.getId();

        // 2. 构造库存扣减消息
        Map<String, Object> messageContent = new HashMap<>();
        messageContent.put("skuId", skuId);
        messageContent.put("num", num);
        messageContent.put("orderId", orderId);

        // 3. 写入本地消息表（和订单创建在同一个本地事务）
        LocalMessage message = new LocalMessage();
        message.setBizId(orderId);
        message.setBizType("order_create");
        message.setMessageContent(JSON.toJSONString(messageContent));
        message.setStatus(0); // 待发送
        message.setSendTimes(0);
        message.setMaxRetry(3);
        message.setNextRetryTime(new Date()); // 立即重试
        localMessageMapper.insert(message);

        return orderId;
    }
}
```

##### 步骤 2：定时任务发送消息（重试机制）

java



运行









```
@Component
@Slf4j
public class LocalMessageJob {
    @Autowired
    private LocalMessageMapper localMessageMapper;
    @Autowired
    private RestTemplate restTemplate;

    // 每10秒执行一次
    @Scheduled(fixedRate = 10000)
    public void sendPendingMessages() {
        // 1. 查询待发送/重试的消息
        List<LocalMessage> pendingMessages = localMessageMapper.selectByStatusAndRetryTime(
            Arrays.asList(0, 1), // 待发送、发送中
            new Date() // 下次重试时间 <= 当前时间
        );

        for (LocalMessage message : pendingMessages) {
            try {
                // 2. 先更新消息状态为「发送中」（防止重复发送）
                localMessageMapper.updateStatus(message.getId(), 1);

                // 3. 调用库存服务扣减库存
                String content = message.getMessageContent();
                Map<String, Object> contentMap = JSON.parseObject(content, Map.class);
                String url = "http://inventory-service/api/stock/deduct";
                ResponseEntity<String> response = restTemplate.postForEntity(
                    url, contentMap, String.class
                );

                // 4. 调用成功：更新消息状态为「已成功」
                if (response.getStatusCode().is2xxSuccessful()) {
                    localMessageMapper.updateStatus(message.getId(), 2);
                    log.info("消息发送成功，订单ID：{}", message.getBizId());
                } else {
                    throw new RuntimeException("库存服务返回非200");
                }
            } catch (Exception e) {
                // 5. 调用失败：更新重试次数+下次重试时间
                int newSendTimes = message.getSendTimes() + 1;
                if (newSendTimes >= message.getMaxRetry()) {
                    // 超过最大重试次数：标记为失败，人工介入
                    localMessageMapper.updateStatusAndRetry(
                        message.getId(), 3, newSendTimes, null
                    );
                    log.error("消息重试次数耗尽，订单ID：{}", message.getBizId(), e);
                } else {
                    // 未超过：下次重试时间（指数退避，比如1分钟后）
                    Date nextRetryTime = new Date(System.currentTimeMillis() + 60 * 1000 * newSendTimes);
                    localMessageMapper.updateStatusAndRetry(
                        message.getId(), 0, newSendTimes, nextRetryTime
                    );
                    log.warn("消息发送失败，订单ID：{}，重试次数：{}", message.getBizId(), newSendTimes);
                }
            }
        }
    }
}
```

##### 步骤 3：库存服务实现（幂等处理）

java



运行









```
@Service
public class StockService {
    @Autowired
    private StockMapper stockMapper;

    // 扣减库存（必须做幂等，防止消息重复发送）
    @Transactional(rollbackFor = Exception.class)
    public void deductStock(Long skuId, Integer num, Long orderId) {
        // 1. 幂等校验：是否已经扣减过该订单的库存
        Integer count = stockMapper.countDeductRecord(skuId, orderId);
        if (count > 0) {
            log.info("订单{}已扣减过库存，幂等返回", orderId);
            return;
        }

        // 2. 扣减库存（加行锁，防止并发问题）
        int updateCount = stockMapper.deductStock(skuId, num);
        if (updateCount == 0) {
            throw new RuntimeException("库存不足，skuId：" + skuId);
        }

        // 3. 记录扣减记录（用于幂等）
        stockMapper.insertDeductRecord(skuId, orderId, num);
    }
}
```

### 本地消息表核心特点（电商场景适配）

- **优点**：无中间件依赖（只需要数据库）、实现简单、兼容性强（适合所有电商系统）；
- **缺点**：侵入业务代码（需要手动写消息表）、消息表和业务表耦合、重试逻辑需要自己维护；
- **适用场景**：中小电商系统、对中间件依赖敏感的场景。

------

## 二、事务消息（基于 MQ 的最终一致性方案，以 RocketMQ 为例）

### 核心思想

利用 MQ 的「事务消息」特性，将「业务操作」和「消息发送」拆分为两步：

1. 半消息：先发送一条「不可被消费」的半消息到 MQ；
2. 本地事务：执行本地业务操作（创建订单）；
3. 确认消息：根据本地事务结果，确认半消息是否转为「可消费」（库存服务消费扣减库存）。

### 实现步骤（电商下单场景）

#### 1. 前置准备

- 引入 RocketMQ 依赖；
- 配置 RocketMQ 生产者 / 消费者；
- 库存服务实现 MQ 消费者（扣减库存）。

#### 2. 代码实现

##### 步骤 1：订单服务发送事务消息

java



运行









```
@Service
@Slf4j
public class OrderTransactionService {
    @Autowired
    private RocketMQTemplate rocketMQTemplate;
    @Autowired
    private OrderMapper orderMapper;

    // 创建订单并发送事务消息
    public Long createOrderWithTransaction(Long userId, Long skuId, Integer num) {
        // 1. 构造订单对象（预创建）
        Order order = new Order();
        order.setUserId(userId);
        order.setSkuId(skuId);
        order.setNum(num);
        // 先不插入数据库，通过本地事务执行

        // 2. 构造消息参数
        Map<String, Object> message = new HashMap<>();
        message.put("userId", userId);
        message.put("skuId", skuId);
        message.put("num", num);
        message.put("order", order); // 携带订单信息

        // 3. 发送事务消息（半消息）
        String transactionId = UUID.randomUUID().toString();
        rocketMQTemplate.sendMessageInTransaction(
            "order-stock-transaction-group", // 生产者组
            "order-stock-topic", // 消息主题
            MessageBuilder.withPayload(JSON.toJSONString(message)).build(),
            transactionId // 自定义参数，传递到本地事务
        );

        // 4. 等待本地事务执行完成后，返回订单ID（实际需根据业务调整）
        return order.getId();
    }

    // 本地事务执行器（RocketMQ回调）
    @RocketMQTransactionListener(txProducerGroup = "order-stock-transaction-group")
    public class OrderTransactionListener implements RocketMQLocalTransactionListener {
        @Override
        public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
            try {
                // 1. 解析消息内容
                String payload = new String((byte[]) msg.getPayload(), StandardCharsets.UTF_8);
                Map<String, Object> content = JSON.parseObject(payload, Map.class);
                Order order = JSON.parseObject(JSON.toJSONString(content.get("order")), Order.class);

                // 2. 执行本地事务：创建订单（核心）
                orderMapper.insert(order);
                log.info("本地事务执行成功，订单ID：{}", order.getId());

                // 3. 本地事务成功：提交消息（转为可消费）
                return RocketMQLocalTransactionState.COMMIT;
            } catch (Exception e) {
                log.error("本地事务执行失败", e);
                // 4. 本地事务失败：回滚消息（删除半消息）
                return RocketMQLocalTransactionState.ROLLBACK;
            }
        }

        // 事务回查（MQ未收到确认时，主动查询本地事务状态）
        @Override
        public RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
            try {
                // 1. 解析消息，获取订单信息
                String payload = new String((byte[]) msg.getPayload(), StandardCharsets.UTF_8);
                Map<String, Object> content = JSON.parseObject(payload, Map.class);
                Order order = JSON.parseObject(JSON.toJSONString(content.get("order")), Order.class);

                // 2. 查询订单是否存在（判断本地事务是否成功）
                Order dbOrder = orderMapper.selectById(order.getId());
                if (dbOrder != null) {
                    // 订单存在：提交消息
                    return RocketMQLocalTransactionState.COMMIT;
                } else {
                    // 订单不存在：回滚消息
                    return RocketMQLocalTransactionState.ROLLBACK;
                }
            } catch (Exception e) {
                // 异常：暂不处理，等待下次回查
                return RocketMQLocalTransactionState.UNKNOWN;
            }
        }
    }
}
```

##### 步骤 2：库存服务消费消息（扣减库存）

java



运行









```
@Service
@Slf4j
public class StockConsumerService {
    @Autowired
    private StockMapper stockMapper;

    // 消费订单创建消息，扣减库存
    @RocketMQMessageListener(
        topic = "order-stock-topic",
        consumerGroup = "stock-consumer-group"
    )
    public class StockConsumer implements RocketMQListener<String> {
        @Override
        @Transactional(rollbackFor = Exception.class)
        public void onMessage(String message) {
            try {
                // 1. 解析消息
                Map<String, Object> content = JSON.parseObject(message, Map.class);
                Long skuId = Long.valueOf(content.get("skuId").toString());
                Integer num = Integer.valueOf(content.get("num").toString());
                Long orderId = Long.valueOf(content.get("order").toString());

                // 2. 幂等校验（防止重复消费）
                Integer count = stockMapper.countDeductRecord(skuId, orderId);
                if (count > 0) {
                    log.info("订单{}已扣减库存，幂等返回", orderId);
                    return;
                }

                // 3. 扣减库存
                int updateCount = stockMapper.deductStock(skuId, num);
                if (updateCount == 0) {
                    throw new RuntimeException("库存不足，skuId：" + skuId);
                }

                // 4. 记录扣减记录
                stockMapper.insertDeductRecord(skuId, orderId, num);
                log.info("订单{}扣减库存成功", orderId);
            } catch (Exception e) {
                log.error("扣减库存失败", e);
                // 抛出异常，让MQ重试（RocketMQ默认重试16次，指数退避）
                throw new RuntimeException("消费消息失败，触发重试", e);
            }
        }
    }
}
```

### 事务消息核心特点（电商场景适配）

- **优点**：无业务代码侵入（消息发送和业务解耦）、MQ 自带重试 / 回查机制、性能更高（异步解耦）；
- **缺点**：依赖特定 MQ（如 RocketMQ/Kafka 不原生支持，需自己实现）、排查问题稍复杂；
- **适用场景**：中大型电商系统、高并发场景（如 618 / 双 11）、对代码侵入性要求高的场景。

## 三、两种方案对比（电商场景选型）

表格







|    维度     |         本地消息表          |   事务消息（RocketMQ）    |
| :---------: | :-------------------------: | :-----------------------: |
|    依赖     |          仅数据库           |     数据库 + RocketMQ     |
| 代码侵入性  | 高（需手动写消息表 / 重试） | 低（MQ 回调 + 自动重试）  |
|    性能     |    一般（定时任务轮询）     |    高（异步消息推送）     |
|  运维成本   |    低（只需维护数据库）     |   中（需维护 MQ 集群）    |
|  适用场景   |      中小电商、低并发       |    中大型电商、高并发     |
| 幂等 / 重试 |         需自己实现          | MQ 自带重试，幂等需自己做 |

------

### 总结

1. **本地消息表**：核心是「本地事务 + 定时重试」，无中间件依赖，实现简单，适合中小电商系统快速落地，重点要做好**幂等校验**和**重试次数控制**；
2. **事务消息**：核心是「半消息 + 本地事务回调 + MQ 重试」，解耦性强、性能高，适合高并发电商场景，重点依赖 MQ 的**事务回查**和**重试机制**，需注意 MQ 集群的可用性；
3. 无论哪种方案，**幂等性**（防止重复执行）、**重试机制**（失败补偿）、**监控告警**（失败消息人工介入）是电商场景下必须做好的三个关键点。
