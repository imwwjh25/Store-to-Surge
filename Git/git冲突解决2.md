## FAT 多分支并行开发重要风险点

fat 环境可以同时部署分支 1、分支 2、分支 3，各个分支独立运行测试。

1. push 自己分支的时候，别的分支提交不会阻拦你的 push 操作。
2. **真正风险不在 push 阶段，而在后续合并 master 主干的时候**。

分支 1、2、3 都是基于旧基线创建，当其中一个分支优先合并 master 上线生产，剩下其余分支合并 master 时会爆发大量冲突。

### 团队开发最佳实践

1. push 代码前，只同步**自己对应的远程特性分支**，不需要同步 master，避免引入无关冲突。
2. fat 自测完成，准备往 uat 环境推进前，**必须合并 master 主干**，同步生产基线代码，解决冲突并且做回归测试。
3. 如果开发周期较长，建议定期 merge master，不要把所有冲突堆积到上线 pro 前一次性处理。

## 踩坑风险清单

表格

| 错误操作                                           | 风险后果                                                     |
| -------------------------------------------------- | ------------------------------------------------------------ |
| push 被拒绝直接执行 `git push -f` 强制推送共享分支 | 覆盖远程分支同事提交，造成代码丢失                           |
| 误认为其他分支提交导致当前分支 push 失败           | 概念混淆，别的分支改动不会阻断当前分支 push                  |
| fat 并行开发全程不 merge master                    | 上线合并 master 时冲突爆炸，容易引入逻辑 bug 流入 pre/pro 环境 |
| 冲突解决完成后不做回归测试                         | 冲突处理有误，破坏已有业务逻辑                               |

## 面试简答

> fat 环境多个特性分支并行，同事在分支 2、3 提交代码，并不会导致我分支 1 push 被拒绝。push 被拒绝说明远程分支 1 已经存在其他人提交，本地版本落后远程。共享分支使用 git fetch + git merge origin / 分支 1，处理完冲突再推送；单人开发分支才可以使用 rebase。 虽然 fat 可以多分支分开部署测试，但进入 uat 之前需要合并 master 同步主干基线；长周期开发也要定期同步 master，避免上线前集中爆发大量冲突。

## 延伸思考：更新项目之后看到其他人提交记录

执行更新操作之后 git log 能看到别人的提交记录，分两种情况：

1. `merge origin/分支1`：看到的是**本分支同事提交**，属于当前需求内的变更；
2. `merge origin/master`：看到的是**主干上其他需求全部提交记录**，代码会同步到本地，属于正常现象。

> 别人的提交记录只是历史，push 合并回 master 不会造成重复合并，Git 依靠 commit id 识别已经合并过的提交。 不需要每次 push 都 merge master，防止提交日志混杂大量无关记录。
