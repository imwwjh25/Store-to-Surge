# 为什么不推荐使用 Java 原生序列化？

Java 原生序列化（`java.io.Serializable`）是 JDK 自带的对象序列化机制，**能实现但绝不推荐在生产环境使用**，核心原因是：**安全性极差、性能差、兼容性差、灵活性低**，几乎是业界公认的 “反面教材”。

下面用最清晰、最实用的角度给你讲透：

------

## 一、最致命的问题：**严重的安全漏洞**

这是**禁止使用**的首要原因。

Java 原生序列化在**反序列化时会执行对象里的代码逻辑**，黑客只要构造恶意序列化数据，发送给服务端，就能：

- 远程执行任意代码（RCE）
- 控制服务器
- 窃取 / 篡改数据

**几乎所有 Java 中间件的高危漏洞，都和原生序列化有关**：

- Fastjson 早期漏洞
- WebLogic、JBoss、Shiro 反序列化漏洞
- Redis、Dubbo 反序列化漏洞

只要你的服务用了原生序列化，就等于**给黑客留了后门**，而且**没有完美的修复方案**，只能彻底不用。

------

## 二、性能极差：又慢又臃肿

1. 序列化后体积超大

   

   原生序列化会把类名、字段名、继承关系、元数据全部写进去，数据量是 JSON/Protobuf 的几倍甚至十几倍。

2. 序列化 / 反序列化速度慢

   

   反射多、开销大，在高并发场景下会严重拖慢接口性能。

3. 网络传输浪费带宽

   

   微服务、分布式场景下，数据越大越耗流量、延迟越高。

------

## 三、兼容性极差：几乎无法升级

1. 类一修改就无法反序列化

   

   只要改字段、加方法、改包名、升级类结构，

   老数据直接无法读取

   ，会抛 

   ```
   InvalidClassException
   ```

   。

2. 必须手动写 serialVersionUID

   

   忘写、写错都会导致兼容崩溃，非常脆弱。

3. 跨语言完全不能用

   

   序列化后的数据

   只能 Java 读

   ，Go/Python/Node.js 都无法解析，现代微服务不可能只用 Java。

------

## 四、使用体验差：侵入性强

1. 必须实现 `Serializable` 接口，**侵入业务代码**
2. 不能序列化 transient 字段
3. 不支持自定义序列化规则（很难优化）
4. 调试困难，二进制数据肉眼完全看不懂

------

## 五、现代开发用什么替代？

业界早就全面抛弃 Java 原生序列化，统一使用这些方案：

表格







|        序列化方案        |               优点               |         适用场景         |
| :----------------------: | :------------------------------: | :----------------------: |
| **JSON**（Jackson/Gson） |       可读性好、通用、安全       |  HTTP 接口、配置、日志   |
|       **Protobuf**       | 速度最快、体积最小、安全、兼容好 | 微服务、gRPC、高性能存储 |
|         **Kryo**         |          速度快、体积小          |  本地缓存、内部数据传输  |
|       **Hessian**        |          跨语言、兼容好          |    Dubbo 等 RPC 框架     |

------

## 六、一句话总结

**Java 原生序列化 = 不安全 + 慢 + 大 + 不兼容 + 难维护**

**任何生产项目都不应该使用**。

------

### 总结

1. **安全风险是第一禁用理由**（反序列化漏洞 = 服务器沦陷）
2. 性能、体积、兼容性全面落后现代序列化方案
3. 现代开发统一用：**JSON / Protobuf / Kryo**
4. 面试问这个问题，**答安全漏洞 + 兼容性差 + 性能差** 就能拿满分
