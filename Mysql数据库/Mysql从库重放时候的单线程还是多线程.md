### 11. Relaylog 重放：单线程 vs 多线程

从库重放 Relaylog 的线程模型，MySQL 不同版本有重大变化，核心结论先明确：

表格







| MySQL 版本 |     重放线程模型     |               核心特点               |
| :--------: | :------------------: | :----------------------------------: |
|   ≤ 5.5    | 单线程（SQL_THREAD） |     所有事务串行执行，从库延迟高     |
| 5.6 - 5.7  |   多线程（基于库）   |    不同库的事务并行执行，同库串行    |
|    8.0+    |  多线程（基于事务）  | 无冲突的事务可并行执行，延迟大幅降低 |

#### 详细解释

1. **MySQL ≤5.5：单线程（SQL_THREAD）**

   

   - 只有 1 个 SQL 线程读取 Relaylog 并执行，无论主库并发多高，从库都串行重放；
   - 问题：主库高并发时，从库延迟会急剧升高（比如主库 TPS 1 万，从库只能处理几千）。

   

2. **MySQL 5.6+：多线程复制（基于库）**

   

   - 引入 `slave_parallel_workers` 参数（设置并行线程数）；
   - 核心逻辑：**不同数据库的事务分配到不同线程执行**，同一数据库的事务仍串行；
   - 适用场景：主库有多个独立数据库（比如 db1、db2、db3），能提升并行度；
   - 局限：若所有事务都在同一个库（比如只有 db1），仍等价于单线程。

   

3. **MySQL 8.0+：多线程复制（基于事务 / 组提交）**

   

   - 基于主库的「组提交（Group Commit）」机制：主库中同一组提交的事务，从库可并行执行；
   - 核心逻辑：主库将事务按「提交组」标记，从库读取到同一组的事务，分配到不同线程并行重放（只要事务无冲突）；
   - 优势：即使单库高并发，也能充分利用多核，大幅降低从库延迟。

   

------

### 12. 从库如何区分不同 Group 实现并行复制

MySQL 8.0 是「组提交 + 事务无冲突检测」的核心，5.6/5.7 是「基于库分区」，分两种情况解释：

#### 情况 1：MySQL 5.6/5.7（基于库的 Group 划分）

1. **Group 划分规则**：按「数据库名」哈希分区

   

   - 从库维护一个「库名 → 线程 ID」的映射表；
   - 读取 Relaylog 时，解析出事务所属的数据库，根据库名哈希分配到对应的并行线程；
   - 同一数据库的事务，强制分配到同一个线程（保证串行，避免数据冲突）。

   

2. **举例**：

   

   - 事务 1：`INSERT INTO db1.t1 VALUES (1)` → 分配到线程 1；
   - 事务 2：`UPDATE db2.t2 SET a=1` → 分配到线程 2；
   - 事务 3：`DELETE FROM db1.t3 WHERE id=1` → 分配到线程 1（和事务 1 同库，串行执行）。

   

3. **核心参数**：

   

   ini

   

   

   

   

   

   ```
   slave_parallel_type = DATABASE  # 按库分区（默认）
   slave_parallel_workers = 4      # 并行线程数（建议设为CPU核心数）
   ```

   

#### 情况 2：MySQL 8.0（基于事务组的 Group 划分）

核心依赖主库的「组提交」和从库的「事务依赖检测」，流程如下：

1. **主库标记事务组**：

   

   - 主库开启 `binlog_group_commit_sync_delay` 等参数，将短时间内提交的事务组成「提交组（Commit Group）」；
   - 每个事务在 binlog 中记录「所属组 ID（group_id）」和「事务依赖信息（last_committed）」。

   

2. **从库解析 Group 并分配线程**：

   

   - 从库读取 Relaylog 时，解析出事务的 `group_id` 和 `last_committed`；
   - 规则：`last_committed` 相同的事务属于同一组，可并行执行；`last_committed` 不同的事务，需按顺序执行（有依赖）；
   - 从库维护「事务依赖表」，检测无冲突的事务分配到不同线程，有冲突的事务等待前置事务完成。

   

3. **举例**：

   

   表格

   

   

   

   | 事务 ID | group_id | last_committed | 并行性 |         分配线程          |
   | :-----: | :------: | :------------: | :----: | :-----------------------: |
   |   T1    |    1     |       0        |  并行  |          线程 1           |
   |   T2    |    1     |       0        |  并行  |          线程 2           |
   |   T3    |    2     |       1        |  串行  | 等待 T1/T2 完成后，线程 3 |

   

4. **核心参数**：

   

   ini

   

   

   

   

   

   ```
   slave_parallel_type = LOGICAL_CLOCK  # 基于事务组（8.0默认）
   slave_parallel_workers = 8           # 并行线程数
   binlog_order_commits = ON            # 主库保证组内事务顺序
   ```

   

#### 关键补充

- 无论哪种 Group 划分，核心原则是「**无冲突的事务才能并行**」（比如修改同一行的事务，必须串行）；
- 8.0 的「逻辑时钟（LOGICAL_CLOCK）」是最优方案，无需手动划分 Group，由 MySQL 自动检测；
- 若从库并行线程数设为 0，会退化为单线程复制。

------

### 总结

1. **Doublewrite 机制**：核心是「先写双写缓冲，再写数据页」，解决页部分写入导致的损坏问题，生产环境必须开启；
2. **主从复制流程**：主库写 binlog → 从库 IO 线程拉取 binlog 写 Relaylog → 从库 SQL 线程重放 Relaylog；
3. **重放线程模型**：5.5 单线程、5.6+ 按库多线程、8.0+ 按事务组多线程（最优）；
4. **Group 划分规则**：5.6/5.7 按数据库哈希分区，8.0 基于主库组提交的逻辑时钟自动划分，核心是保证无冲突事务并行。
